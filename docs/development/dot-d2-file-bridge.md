# Dot D2：受控文件交付桥

任务 [#14](https://github.com/alongor666/InsurHOT/issues/14)，父任务 [#8](https://github.com/alongor666/InsurHOT/issues/8)；合同与边界见 [Dot 信息接入规划](dot-integration-plan.md)。

这是 D2 的第一种交付通道，也是规划第 8 节写明的退路：**交付者把 v1 JSON 批次落盘到一个收件目录，运营者机器上的桥把它提交到 InsurHOT 自己的 `POST /api/ingest/dot`，保存服务器回执并归档。** 它不是「官方 Dot API」，不假设 Dot 有 REST API 或 webhook；不调用任何模型，不访问批次里的来源链接，不触发分析、队列、推送或公开发布。

**当前状态**：桥已实现，并在本机对真实的接收端与真实 PostgreSQL 验证（见文末）。**真实 Dot 账户连接与首批真实 Dot 数据：NOT RUN**——账户连接尚未完成，Dot 能否把文件写到运营者机器上的目录也还没有在真实账户里核实。

## 用法

```
DOT_INGEST_TOKEN=<专用凭据> node scripts/dot-bridge.ts --inbox <收件目录> [--endpoint https://<主机>/api/ingest/dot]
```

- 跑一轮就退出。要定时执行，由运营者自己的调度器（cron、launchd 等）调用；桥本身不常驻、不自带定时。
- **凭据**只从环境变量 `DOT_INGEST_TOKEN` 读取，不接受命令行参数（命令行对同机其他进程可见）。它不会出现在任何输出、台账、回执或错误文件里。取值与服务端的 `DOT_INGEST_TOKEN` 相同，由私有凭据渠道配置，不入 Git、不写进交给 Dot 的说明。
  - **与规划的口径差异（需 owner 知情）**：规划第 4 节 D2 的通过条件写的是「专用凭据仅服务端保管」。用这座桥时，运行桥的那台运营者机器也持有同一个凭据；Dot 本身不持有，凭据也不进入文件、提示词或对话。如果要求凭据严格只在服务端，就得换成服务端侧的通道（例如服务端自己去读一个共享目录），那是另一种部署。
- **端点**来自 `--endpoint` 或环境变量 `DOT_BRIDGE_ENDPOINT`，必须是完整的 `/api/ingest/dot` 地址、不带查询串和内嵌凭据；除本机地址（`localhost`、`127.0.0.1`、`[::1]`）外必须是 `https`。不跟随重定向。
- 服务端要先启用接收：`DOT_INGEST_ENABLED=true` 且 `DOT_INGEST_TOKEN` 是一个至少 32 字符的非占位值（规划第 5 节）。缺省关闭时桥会收到 503，文件原样等待。

## 收件目录

```
<收件目录>/
  pending/      待交付：只处理这一层、扩展名为 .json 的普通文件
  delivered/    <deliveryId>.json：发出去的那份字节
  receipts/     <deliveryId>.json：服务器回执（重复交付时更新，时间仍是首次接收的时间）
  rejected/     被永久拒绝的文件与 <文件名>.error.json（HTTP 状态、错误代码、时间）
  ledger.jsonl  台账：每处理一个文件一行
  .aside/       桥的内部暂存（见下）；正常结束时是空的
  .lock         运行中的桥的进程号
```

目录与文件由桥以 0700 / 0600 创建。**落盘约定**：交付者先写 `<名字>.json.part`，写完再改名为 `<名字>.json`，文件名建议就用批次 ID。桥会跳过 `.part`、隐藏文件、子目录、符号链接，以及最近 5 秒内还被修改过的文件。不要把 `pending/`、`delivered/`、`receipts/`、`rejected/` 本身做成指向别处的符号链接：桥不检查这一点，那样写入会落到收件目录之外。

**一次请求要花时间，这期间交付者可能在同一个文件名下放了新文件。** 桥因此这样做：

- 打开文件时不跟随符号链接，判断（是不是普通文件、大小、修改时间）和读取都经过同一个文件描述符——被判断的就是被发送的；
- 归档写的是**发出去的那份字节**，不是事后去移动那个路径上的东西；
- 要拿走 `pending/` 里的文件时，先把它一步移到 `.aside/`，在那里核对它就是发出去的那一份（设备号、inode、大小、修改时间都相同）才删除或归入 `rejected/`；不是同一份就原样放回 `pending/`（不覆盖任何已有文件），等下一轮按它自己的内容处理。
- 上一轮被强行终止而留在 `.aside/` 的文件，下一轮开始时放回 `pending/`（名字是 `recovered-….json`），重新交付；服务器幂等，不会重复入库。

## 每个文件的结果

| 情形 | 文件去向 | 台账 `outcome` |
|---|---|---|
| 服务器回执 `received` | `delivered/` | `delivered` |
| 服务器回执 `duplicate`（同一 `deliveryId`、同一内容已收过） | `delivered/` 里已有的第一份保留；`pending/` 里这一份在确认是发出去的那份之后删除；回执更新（时间仍是首次接收的时间） | `duplicate` |
| 400 格式不合法、409 同 `deliveryId` 内容不同、413 超限、415 | `rejected/`，附 `.error.json` | `rejected` |
| 发送前就能判定不可用：超过 256 KiB、不是 JSON、没有字符串 `deliveryId`、`deliveryId` 不符合合同的安全 ID 规则 | `rejected/`（不发请求，保留原文件名） | `rejected` |
| 网络不通、超时、重定向、401/403、429、5xx（含 503 接收未启用）、2xx 但不是这份批次的回执（`ok` 不为真、`deliveryId` 不符）、本机文件操作出错 | **留在 `pending/`，字节不变** | `retry` |
| 符号链接、子目录、刚修改过 | 留在 `pending/` | `skipped` |

接收端目前把请求解析阶段的一切非 413/415 错误都报成 400（`apps/api/src/routes/dot-ingest.ts` 的错误处理），桥把 400 当作永久拒绝。所以一个因服务端解析异常而得到 400 的合法批次也会进 `rejected/`；文件和原因都还在，可以人工放回 `pending/`。

401/403（凭据有问题）、429（速率窗口已满）和网络不通会结束本轮，后面的文件不再发送。重试始终用同一个文件、同一个 `deliveryId`；接收端按 `deliveryId` 幂等，重复提交不新增数据。被 409 拒绝的批次要由交付者换一个新的 `deliveryId` 重新落盘。

台账每行只有：`at`、`file`、`deliveryId`、`outcome`、`httpStatus`、`receivedAt`、`firstSeenAt`、`itemCount`、`error`。不含标题、摘要、来源链接或凭据。

**退出码**：0 没有遗留；2 有文件等待重试（或另一个桥正占着锁）；3 有文件被永久拒绝；1 配置错误（缺凭据、端点不合规、未知参数）。标准输出是一行 JSON 计数。

**一次只跑一个（尽力而为）**：`.lock` 独占创建；已有且进程还在，第二个桥什么都不做；进程已不在则接管；没有内容的锁文件在 10 秒内视为正在启动的持有者。接管不是原子的，极端情况下两个桥可能同时运行——**这不会丢批次也不会重复入库**：两边发的是同样的字节，服务器只存一份，每一步文件操作都容忍对方已经做过。进程号被无关进程复用时，锁会一直显得有人持有（退出码 2）；确认没有桥在运行后手工删除 `<收件目录>/.lock` 即可。

## 失败与回退

- 桥在「回执已写、文件未移动」之间中断：下一轮得到 `duplicate` 并完成归档。
- 服务器已入库但回执丢失：下一轮得到 `duplicate`，回执里的时间是首次接收的时间。
- 停用：不再调用脚本即可；服务端关闭 `DOT_INGEST_ENABLED` 或撤销凭据后，文件留在 `pending/` 等待。桥不删除任何未被服务器确认的文件。
- 回退代码：revert 本 PR；不涉及数据库结构。

## 给 Dot 的责任说明（待配置，不是已建立的任务）

连接完成后可以直接交给 Dot 的文字。它描述的是待配置的方案；目前没有创建任何真实的 Dot 责任、连接或定时计划。

> 你负责持续关注保险行业的公开信息：重要变化、保险产品及其评价标准、AI 带来的新商业模式。保持行业客观，不偏向任何一家保险公司。
>
> 每个工作日北京时间 09:00 前交付一个常规批次；出现重大事件时另行交付。每个批次是一个 JSON 文件，先写成 `<批次ID>.json.part`，写完后改名为 `<批次ID>.json`，放进约定的收件目录的 `pending/`。
>
> 文件内容：`schemaVersion` 固定为 `insurhot.dot.v1`；`deliveryId` 是这个批次稳定的 ID（1–80 个字符，只用字母、数字、`.`、`_`、`-`，以字母或数字开头），同一批次重试时不变，内容有任何修改就换新 ID，文件名也用新 ID；`items` 有 1–50 条，整个文件不超过 256 KiB。每条包含：
>
> - `itemId`：批内唯一，字符规则与 `deliveryId` 相同；
> - `title`：1–500 字符，不能全是空白；
> - `summary`：1–4000 字符，不能全是空白，必须是你自己写的摘要，不要粘贴原文；
> - `pillars`：`matters`、`changes`、`emerges` 中的 1–3 个，不重复；
> - `assertionKind`：来源明确报道的写 `reported`，你自己的推断写 `inference`；
> - `sources`：1–10 个原始来源，每个有 `url`（`https`，不超过 2048 字符，不带用户名或密码）、`publisher`（1–200 字符）、`publishedAt`（带时区的 ISO 8601 时间，如 `2026-09-29T08:00:00+08:00` 或以 `Z` 结尾；不知道就写 `null`）；
> - `dotObservedAt`：你看到这条信息的时间，同样是带时区的 ISO 8601。
>
> 任何层级都不要添加其他字段，否则整批会被拒绝。一个合法的批次：
>
> ```json
> {
>   "schemaVersion": "insurhot.dot.v1",
>   "deliveryId": "dot-2026-09-30-daily",
>   "items": [
>     {
>       "itemId": "item-1",
>       "title": "某监管机构发布车险定价新规征求意见稿",
>       "summary": "征求意见稿拟调整商业车险自主定价系数的浮动范围。以下是我对原文的归纳，不是原文摘录。",
>       "pillars": ["changes"],
>       "assertionKind": "reported",
>       "sources": [
>         { "url": "https://example.org/notice", "publisher": "示例监管机构", "publishedAt": "2026-09-29T10:00:00+08:00" }
>       ],
>       "dotObservedAt": "2026-09-30T08:30:00+08:00"
>     }
>   ]
> }
> ```
>
> 优先保留原始文件的链接与发布者；同一事件的重复报道合并成一条；区分报道与你的推断。访问不到的来源如实写明，不要声称读过。不要购买订阅，不要向任何公开渠道发布，不要把任何凭据写进文件或对话。

## 验证（本机，PostgreSQL 18.1，一次性库 `*_test`）

`tests/dot-bridge.test.ts`，11 个用例（评审第 1 轮时是 8 个）：在测试进程里把本仓的 API 应用监听在 `127.0.0.1` 的临时端口，启用接收并使用每次运行随机生成的凭据；批次是合成数据。文档里那份给 Dot 的合法样例，测试没有提交过它。

- 交付一次并归档，库里一行批次一行条目；同一文件重交付与「同内容、键序不同」都是 `duplicate`，库里不新增，回执时间等于首次接收时间。
- 同 `deliveryId` 不同内容得到 409，未知字段得到 400，都进入 `rejected/`；库里原批次的哈希不变。
- 超限、非 JSON、缺 `deliveryId`、`deliveryId` 为 `../../escaped` 的文件不发请求直接拒绝；符号链接、子目录、`.part`、隐藏文件、刚修改的文件不处理；收件目录之外没有任何写入。
- 接收未启用（503）、端口无人监听、凭据错误（401）时文件字节不变地留在 `pending/`，之后用同一 `deliveryId` 交付成功。
- 重定向不被跟随（重定向目标收到 0 个请求）；429 结束本轮；200 但 `deliveryId` 不符、`ok` 为假或缺失、状态为 500 而正文像回执，都不算回执。
- 发送途中同名文件被替换（首次接收、重复、被拒三种结局各一次）：归档与拒收保存的都是发出去的字节，新文件留在 `pending/`，下一轮按它自己的内容交付。
- `x` 与 `x.receipt` 两个批次 ID 的归档和回执互不覆盖；被拒文件名恰好是另一个被拒文件的原因文件名时，先前的文件不被覆盖。
- 发送途中另一个待交付文件被撤走，本轮照常完成；`.aside/` 里的遗留文件被放回并交付；两个不加锁的桥同时处理 6 个文件，库里 6 个批次各一份，没有被拒、没有遗留。
- 端点校验；锁（持有者在、持有者已不在、两轮同时运行只入库一份）。
- 以子进程运行脚本：汇总与退出码 0/2/3/1；命令行不接受 `--token`；两个凭据都不出现在台账、回执、错误文件、标准输出和标准错误里；台账与回执的权限是 0600。

## 评审第 1 轮后的修改

独立评审（Opus 5.5 只读，绑定 `c1d4cb9`）结论 REQUEST_CHANGES，报告原文在 PR 评论里。文件处理部分因此重写。

| 发现 | 处理 |
|---|---|
| **P1**：请求途中同名文件被替换，没交付的新文件会被错放进 `delivered/`，重复分支下被直接删除 | 归档写发出去的字节；拿走 `pending/` 的文件前先移到 `.aside/` 核对身份，不是同一份就放回 |
| P2：`lstat` 之后文件被换成符号链接，桥会读到并发送目录外的内容 | 以不跟随链接的方式打开，判断与读取走同一个文件描述符 |
| P2：`deliveryId` 以 `.receipt` 结尾时归档与回执互相覆盖或误删 | 回执放进独立目录 `receipts/`；归档只新建、不覆盖 |
| P2：拒收的原因文件可能覆盖先前被拒的原文件 | 选名时同时避开原因文件名；拒收目录里只新建、不覆盖 |
| P2：接管陈旧锁有竞态 | 不再依赖锁的正确性：两个桥同时运行不丢批次、不重复入库（有不加锁的并发用例）；空锁文件 10 秒内视为持有者正在启动。接管本身仍非原子，已写明 |
| P2：给 Dot 的责任说明漏了会导致 400 的约束 | 逐项补齐并附合法样例 |
| P3：单个文件的本地错误会中断整轮 | 记为该文件 `retry`，本轮继续；文件在列出之后消失不算错误 |
| P3：400 的含义与接收端耦合；进程号复用；凭据口径 | 写进文档（结果表下、锁、用法） |
| P3：三个存活的变异（不检查 `ok`、不检查 2xx、凭据写进不可达分支的台账） | 补了用例，三项现在都被发现 |
